# 13.01 Backing up every pebbl store and the multiplayer question

Written 2026-07-30, right after pebbl's own store moved into its repo.

## Where every store actually stands

Measured, not assumed:

| Repo | Entries | Tracked in git | Remote | Survives this laptop dying? |
|---|---|---|---|---|
| pebbl | 265 | yes (events.jsonl) | SkywrightAI/pebbl (public) | **yes**, as of today |
| loom | 327 | **none** | **none** | **no** |
| lawyer-tool-rs | 85 | **none** | **none** | **no** |
| lumr | 81 | only `handoffs.md` | SkywrightAI/lumr (private) | partly |
| harold | 20 | **none** | NewPath-Ai/Harold | **no** |
| frontend-loop | 7 | yes (9 files) | **none** | **no** |
| security | 3 | **none** | NewPath-Ai/security | **no** |

The headline: **loom has the largest store of any repo — 327 entries, more than
pebbl's own — and it is the least protected.** No remote, nothing tracked. It is
also the store the maintenance plane reads to scope its own improvements, so
losing it does not just lose notes, it lobotomises the factory.

lawyer-tool-rs is second by volume and is deliberately local and offline, because
it holds work derived from real contracts. Its answer has to be different from
the others.

## The order I would do these in

**1. loom — highest value, no protection.** It has no remote at all, which is a
deliberate choice (it lands locally on promote). Two ways to fix backup without
undoing that:

- *Give loom a private remote and track `events.jsonl`.* Simplest, matches what
  pebbl now does. The objection to a remote was about the promote flow, not about
  memory; a remote that only ever receives pushes changes nothing about how loom
  lands work.
- *Or push only the store*, as a separate private repo that loom's `.pebbl`
  tracks. Keeps loom itself remote-free. More moving parts, and a second place to
  forget about.

I would take the first. The second optimises for a constraint that may not be
real — worth checking what actually motivated "no remote" before ruling it out.

**2. lawyer-tool-rs — needs a different answer.** Its memory is about a sensitive
codebase, so a GitHub remote is the wrong instinct even private. Options: an
encrypted local backup (Time Machine already covers the disk, if it is running —
worth verifying rather than assuming), or a private remote with the store's
foundation entries left in `events.local.jsonl`. Decide the privacy posture
first, then the transport. Do not default this one to "same as loom".

**3. lumr, harold, security, frontend-loop — mechanical once 1 and 2 are settled.**
Each needs the same two lines: track `events.jsonl` with the shared-mode
gitignore, and make sure something commits it. lumr already tracks `handoffs.md`
only, which is the factory-droplet carve-out; adding `events.jsonl` alongside is
additive.

**4. One committer, not six.** The daily job that now lives in `~/pebbl/ops` is
pebbl-specific. Six copies of it is six things to drift. Better shape: one job
that walks a list of store paths, commits and pushes each, and beats **one**
liveness heartbeat per store so a single dead repo still shows up. That is a real
piece of work, not a copy-paste — worth doing once the individual decisions above
are made, not before.

## The multiplayer question

Worth separating into three questions that get confused with each other.

**(a) Two machines, one person.** Already solved in principle: `events.jsonl` is
append-only text with `merge=union`, which is exactly the shape that merges
without conflict. What is untested is the day-to-day — pulling before writing,
what happens when both sides wrote offline, whether the fold is truly
order-independent under a real union merge. The P0 tracer proved two branches
merge; it did not prove a week of two-machine use.

**(b) Two people, one project.** This is where the real design questions are, and
none of them are transport:

- Whose name is on an entry? `actor` exists but nothing reads it.
- What happens when two people record contradicting decisions? `--corrects`
  supersedes, but it assumes one author who knows the prior entry exists.
- Does a teammate want your `fleeting` entries, or only `foundation`? Right now
  sharing is per-entry and manual.

**(c) pebbl as a product other people run.** Different question again — it needs
`init --shared` to be the default path rather than the opt-in, and it needs the
privacy story to be legible to someone who did not build it. The accept ledger
and the line-scoped marker landed today are both part of that: they are what make
a store safe to keep in a public repo.

My read: (a) is a testing job and could be done this week. (b) is a design spike
and should not start until there is a second person actually using a store —
building multiplayer semantics for a hypothetical collaborator is how you get
features nobody fits. (c) is downstream of (b).

## What I would not do

Copy the `ops/` pipeline into six repos. It works for pebbl because pebbl is
where it lives; duplicating it is the thing that looks like progress and creates
six divergent copies of one job.
